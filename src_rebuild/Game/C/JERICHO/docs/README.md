# JERICHO — Just an Event Relay for In-engine Callbacks, Handlers and Opt-ins

JERICHO is a tiny, platform-neutral C/C++ API that turns REDRIVER2 into a
**host** for mods. There are two kinds of mods, and they are handled very
differently:

## 1. API addons — runtime DLLs (the primary model)

An **addon** is written against the JERICHO API only and is marked
`runtime = "dll"` in its `mod.toml`. It is compiled into a DLL **without
rebuilding the game**: drop it into `JERICHO/MODS/<id>/`, press
**Compile Mods** in the game (Options → JERICHO) — or run
`JERICHO/build_mods.bat` — and the runtime loads it at boot / on reload.
The game exe is never touched. This is what JERICHO is for: developers use
the API, they do not modify the game.

- The loader (`jer_loader.c`) scans `JERICHO/MODS`, reads each `mod.toml`,
  `LoadLibrary`s the compiled `<id>.dll` and resolves its entry
  (`jer_module_<id>_entry`).
- Enable/disable/reorder at runtime via the Mods menu, persisted to
  `JERICHO/CONFIG/modlist.ini`.
- **Addon development** uses the standalone SDK in `JERICHO/sdk/` — API
  headers + the game's import library + `build_mods.bat`. No game source,
  no PsyCross, no SDL/OpenAL/JPEG needed. See `JERICHO/sdk/README.md`.

## 2. Deep mods — compiled into the game

A **deep mod** patches game internals at the source level (it includes game
headers and reads/writes game globals like `player[]`, `car_data[]`).
Because MSVC cannot import game *data* globals into a DLL without
`__declspec(dllimport)`, these mods cannot be external plugins; they are
**compiled in** by premake's auto-scan (a folder with `mod.toml` that does
*not* declare `runtime = "dll"`). The exe exports every game symbol
(functions *and* globals) via `exports.def`, but only functions are usable
from DLL addons.

The in-repo deep mods (crumple, carhacks, cainescrossfire, collisiondevil,
d2pl, sandbox, antfarm, JerAI, levelhacks, testmode, mp, yarisbounce,
gaildrv2, d1cars) work exactly as before: build the game and they are
linked in, managed at runtime through the same Mods menu. Only `debugorbit`
and `example` declare `runtime = "dll"`, so they are the two in-repo
external modules.

## Layout

```
JERICHO/                           the central framework folder (repo + data dir)
    MODS/<id>/                     installed modules (one folder each)
        <id>.dll                   compiled addon binary (built, not committed)
        mod.toml                   metadata (id, name, version, runtime, ...)
        <id>.c                     addon source (runtime="dll") or deep mod source
    CONFIG/
        modlist.ini                module status + load order
        <id>.ini                   per-module settings (jer_config store)
    build_mods.bat                 compiles all runtime="dll" addons (in-game button)
    sdk/                           standalone addon development kit (headers + lib)
src_rebuild/Game/C/JERICHO/        the SDK (ships inside the game dev area)
    include/jericho.h              public API: hooks, events, overrides, module entry
    include/jer_*.h                helpers: math, config, pause/frontend menus,
                                   animation, HUD, screens, textures, map, console,
                                   sound, net, colours, NPCs
    src/jer_loader.c               runtime DLL scanner + loader
    src/jer_system.c               module table, activation, dispatch, logging
    src/jer_compile.c              host-side "Compile Mods" (spawns build_mods.bat)
    src/jer_manager.c              CONFIG/modlist.ini read/write
    src/jer_config.c               per-module CONFIG/<id>.ini key/value store
    src/jer_menu.c / jer_pause_menu.c / jer_screen.c / jer_prompt.c
                                   the menu, screen and prompt helpers
    gen/jer_registry.c             GENERATED by premake (compiled-in deep mods)
src_rebuild/Game/C/jer_map.c       jer_map engine-side impl (region streaming)
src_rebuild/exports.def            GENERATED by tools/gen_exports (game symbols)
src_rebuild/premake5_mods.lua      mods-only build: one DLL project per addon
src_rebuild/tools/gen_exports/     maps the linker map to exports.def
```

## Building the game

Run these from `src_rebuild/` (the `gen_vc2019*.bat` scripts there do the same):

```
premake5.exe vs2019
msbuild build/JERICHO.sln /p:Configuration=Release /p:Platform=x64
```

- premake **auto-scans** `JERICHO/MODS`: every folder with a `mod.toml`
  (no `runtime = "dll"`) becomes a compiled-in module — no mod list to
  maintain anywhere.
- The linker map (`/MAP`) is turned into `exports.def` by
  `tools/gen_exports`, so the exe exports its symbols and DLL addons can
  link against them. Regenerate it only when the game's own symbol set
  changes: build with `/MAP`, run `gen_exports`, commit the new def.

## Building addons (game-side)

```
JERICHO\build_mods.bat
```

or the **Compile Mods** button in the Mods menu (shown whenever a source tree
and the build shim are present, so a shipped package hides it). This runs
`premake5_mods.lua` (generates one DLL project per `runtime = "dll"`
addon), builds them against the game's import library, and copies the DLLs
next to the exe. Reloading the Mods screen activates them. No exe rebuild.

## Building deep mods (game-side)

Deep mods (no `runtime = "dll"`) are compiled **into** the exe. Installing one
from the mod repo asks whether to rebuild when you leave the repo browser;
**Compile Mods** in the Mods menu is the manual path, and both ask first:

- **Yes** closes the game. A detached helper (`JERICHO/build_restart.bat`,
  started before the exit) waits for the process, moves the exe to `<exe>.old`,
  builds the runtime addons, then runs `JERICHO/build_game.bat` (premake, one
  MSBuild step per deep module, then the exe) in a console of its own — the long
  compiler output goes to `JERICHO/CONFIG/build.log`. On success it starts the
  new exe, so the player comes back with the mods in it. On failure it restores
  the old exe, starts it, and leaves `CONFIG/build-failed` for the next boot to
  report.
- Where there is no source tree/toolchain (a shipped install, another platform)
  the deferred path is used instead: the runtime addons build immediately,
  `JERICHO/CONFIG/needs-build` records the deep rebuild, and the next boot runs
  it before the frontend menu, showing a progress screen — `Compiling JERICHO
  addons...` / `CRUMPLE [3/9]`. That boot-time build runs from the live image, so
  it still needs the restart after it; it moves the running exe to `<exe>.old`
  and the freshly linked exe lands under the normal name. The heading and the `[i/n]` line are drawn by the presentation
screen in [screens.md](screens.md).

## The runtime

At boot the game calls `jer_init("JERICHO")`:

1. Fills the module table: compiled-in deep mods (generated registry) +
   runtime-loaded addon DLLs (loader scan).
2. Reads `JERICHO/CONFIG/modlist.ini` (created/edited by the Mods menu).
   Line order = load order, value = enabled state. Absent file = modules
   follow their `default-enabled` flag from `mod.toml`.
3. Activates each enabled module in load order via its entry.
4. Fires `JER_EVENT_BOOT`, prints the banner and a module/hook inventory
   to JERICHO.log.

```
== JERICHO v2 (build 0.9.0) == Just-in-Time Extensible Runtime Interface for ...
[jericho] --- module inventory (14 loaded) ---
[jericho]   carhacks        v0.1.0  enabled=1 src=modlist state=active   author="JERICHO" deps="-"
[jericho]   crumple         v1.0.0  enabled=1 src=modlist state=active   author="Nattdy + DeepSeek" deps="-"
[jericho]   cainescrossfire v0.6.0  enabled=0 src=modlist state=disabled author="JERICHO" deps="carhacks"
[jericho]   mp              v0.1.0  enabled=1 src=modlist state=active   author="JERICHO" deps="-"
[jericho]   example         v0.1.0  enabled=0 src=modlist state=disabled author="DeepSeek" deps="-"
```

|----------|--------------------------|----------------------|
| Windows  | yes                      | yes (`LoadLibrary`)  |
| Linux    | yes                      | yes (`dlopen`)       |
| Emscripten / Android | yes            | no (loader is a stub, logged) |

## Troubleshooting

- **"Compile it first"** for an addon: the folder has no `<id>.dll` yet —
  run Compile Mods / `build_mods.bat`.
- **Addon DLL fails to link with a data symbol** (`?player@@...`): addons
  can call game *functions* and read data through the JERICHO API, but they
  cannot import game *data globals* directly (MSVC limitation). Keep
  addons API-only; move game-internal code into a deep mod.
- **A new game build doesn't show in the Mods menu**: the loader resolves
  mods relative to the game's working directory — make sure `JERICHO/` sits
  next to the exe (the build mirrors it there).
