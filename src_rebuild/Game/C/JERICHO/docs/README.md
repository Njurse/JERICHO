# JERICHO — Just-in-Time Extensible Runtime Interface for Compiled Hooks & Overrides

JERICHO is a tiny, platform-neutral C/C++ API that turns REDRIVER2 into a
**host** for compiled-in modules ("packages"). Modules are built from source
with the same toolchain as the game — no runtime loading, no DLLs, no
`dlopen`/`LoadLibrary`, no platform-specific code anywhere.

The core is **agnostic about which mods are installed**: premake scans
`JERICHO/MODS` at build time and compiles every module it finds, and the
runtime activates the enabled ones at boot from `JERICHO/CONFIG/modlist.ini`.
Install / uninstall a mod = drop / remove one folder and rebuild.

- **Deterministic security** — audit the module source, build it with your
  own toolchain: the bytes you run are the bytes you read.
- **Deterministic versions** — JERICHO's build version is stamped into every
  exe at premake time (git describe), so each release is a reproducible
  JERICHO version.
- **Minimal intrusion** — the vanilla game files only get single inert
  `jer_fire(...)` lines tagged `// JERICHO-HOOK`. With no modules enabled
  those are no-ops: the vanilla build is unchanged.

## Layout

```
JERICHO/                           the central framework folder (repo + data dir)
    MODS/                          installed module packages (one folder each)
        <id>/mod.toml              metadata (id, name, version, author, ...)
        <id>/<id>.c                the module source
    CONFIG/                        all config for installed mods lives here
        modlist.ini                module status + load order (this file)
        <id>.ini                   per-module settings (jer_config store)
src_rebuild/Game/C/JERICHO/        the SDK (ships inside the game dev area)
    include/jericho.h              public API + JER_EVENT_* + MOD_CONTEXT
    include/jer_math.h             core math helpers (ex-Nattdy's nattdymath)
    include/jer_config.h           persistent config API (CONFIG/*.ini)
    src/jer_system.c               registry, dispatch, activation, banner
    src/jer_manager.c              CONFIG/modlist.ini read/write (tiny INI)
    src/jer_config.c               persistent config store (PC only)
    src/jer_math.c                 external float helpers (jer_math)
    src/jer_internal.h             shared manager internals
    gen/jer_registry.c             GENERATED by premake (do not edit)
    docs/                          README.md, events.md, HOOKS.md (this guide)
```

The `JERICHO/` folder is mirrored next to the exe by premake's postbuild
step, so the runtime finds `MODS`/`CONFIG` beside the exe — paths are
resolved relative to the working dir, the same convention the game uses
for its data folder (`gDataFolder`).

## Building with modules

```
premake5.exe vs2019
```

- premake **auto-scans** `JERICHO/MODS` and builds every folder that has a
  `mod.toml` — no mod list to maintain, nothing to edit when you add or
  remove a mod.
- `--with-mods="crumple,example"` is an **optional filter** (build only the
  listed ids); omit it to compile everything installed.
- premake generates `JERICHO/gen/jer_registry.c` from the scan, creates a
  static-lib project per module (`mod_<id>`), links them into the game, and
  copies `JERICHO/` into the build output.

## The runtime

At boot the game calls `jer_init("JERICHO")` (resolved relative to the
working dir, next to the exe — same convention as the data folder):

1. Reads `JERICHO/CONFIG/modlist.ini` (created/edited by the frontend
   **JERICHO** menu under Options). The file is a flat list of
   `id = 1|0` lines — line order is the **load order**, the value is the
   **enabled state**. Absent file = every compiled-in module follows its
   `default-enabled` flag from `JERICHO/MODS/<id>/mod.toml`.
2. Activates each enabled module in load order: calls its
   `jer_module_<id>_entry(ctx)`.
3. Fires `JER_EVENT_BOOT`.
4. Prints the banner:
   `== JERICHO v1 (build 8.0-18-g0f35465f-dirty) == ...`
5. Emits a **boot inventory** (module + hook diagnostics) — see below.

Example `modlist.ini`:

```ini
# JERICHO module list — load order and enabled state.
crumple = 1
d2pl = 1
levelhacks = 1
sandbox = 0
example = 0
```

## Logging & diagnostics

All JERICHO output goes through the game's PsyX logger, so it lands in
**`REDRIVER2.log`** next to the exe (and the debug console in `_DEBUG`
builds) — the game wires `jer_set_logger` at boot in `main.c`. Messages are
level-classified by their own keywords: `warning:` → warning,
`DISABLED`/`error` → error, everything else → info.

At boot (and on every Mods-menu reload) the runtime logs an inventory that
tells you exactly what is going on:

```
[jericho] --- module inventory (3 built-in) ---
[jericho]   crumple    v1.0.0  enabled=1 state=active         author="Nattdy + DeepSeek" deps="-"
[jericho]   camera     v0.1.0  enabled=1 state=active         author="DeepSeek" deps="-"
[jericho]   example    v0.1.0  enabled=0 state=disabled       author="DeepSeek" deps="-"
[jericho] --- hook inventory (16 handler(s)) ---
[jericho]   event=COLLISION          module=crumple    priority=0
[jericho]   event=CAMERA             module=camera     priority=0
...
```

- **state** explains why a module isn't running: `disabled` (modlist),
  `not-activated`, `INVALID` (failed SDK/dependency validation — the
  runtime logs the specific reason above the inventory), or `active`.
- **hook inventory** lists every registered handler with the event it
  listens to, the owning module, and its dispatch priority — a quick way to
  see which of the hooks each installed mod touches.

Modules log through `ctx->jer_log`/`jer_log`; the `[module]` prefix in each
message keeps per-module output greppable in the log file.

Module management happens in the **frontend** (Options → JERICHO): cross
toggles a module, left/right moves its load order, all persisted to
`JERICHO/CONFIG/modlist.ini` and re-applied immediately (safe there — no
session is running). No rebuild needed for toggles.

## Writing a module

```c
#include "jericho.h"

static int myBoot(void* ud, void* args) { ...; return JER_RESULT_CONTINUE; }

JER_MODULE_ENTRY(jer_module_myid_entry)(JERICHO_CONTEXT* ctx)
{
    ctx->jer_register_module(ctx, "myid", "My Module", "1.0.0",
        "You", "what it does", "deps");
    ctx->jer_register_hook(ctx, JER_EVENT_BOOT, myBoot, NULL, 0);
    ctx->jer_log(ctx, "[myid] hello\n");
}
```

`JERICHO/MODS/example/` is a working smoke-test module — copy it to start.

## Events

See `events.md` for the full list of engine-fired events and their argument
structs (in `src_rebuild/Game/C/jer_events.h`). Modules may also fire their
own custom events (`>= JER_EVENT_MODULE_CUSTOM`).

## Install / remove workflow

- **Install**: drop the module folder into `JERICHO/MODS/`, re-run premake,
  rebuild. It is compiled in, registered, and shows up in the Mods menu.
  Enable/disable and reorder at runtime via the menu (persisted to
  `JERICHO/CONFIG/modlist.ini`).
- **Remove**: delete the folder from `JERICHO/MODS/`, re-run premake,
  rebuild. The game reverts to vanilla behavior (the hook lines are inert
  no-ops with no handlers).
- **Version**: every exe release carries its JERICHO build version in the
  boot banner; bump `JERICHO_SDK_VERSION` only on ABI-breaking changes (the
  runtime refuses mismatched modules).
